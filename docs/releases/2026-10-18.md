## Por qué se desalineó

El 18 de octubre se autorizó y realizó una publicación manual por CLI desde
`test/cuatro-mejoras`. El build y el cambio de alias no fusionan ramas Git.
Los PR de app #79–82 y de datos #38 se dejaron abiertos. En la app seguía pendiente
la aprobación exigida por GitHub; eso no significaba que el código hubiera fallado
las pruebas locales. Se publicó la integración sin cerrar después su entrada en

Esta reconciliación incorpora la misma historia probada, no una nueva pasada

No activa el temporizador. Los cuatro heads de los PR de app son antepasados de

```bash

git ls-remote origin 'refs/tags/prod-2026-10-18-ce55bc4' 'refs/tags/prod-2026-10-18-ce55bc4^{}'

```

Esperado: `ls-remote` devuelve el tag anotado y su referencia pelada `^{}`,
esta última con el SHA completo de la tabla. Una salida vacía no es éxito: falta
el anclaje remoto aunque exista un tag local. `rev-parse` devuelve ese mismo SHA;
el último comando termina con código 0. Un `main` que no contenga ese commit no es una
base válida para sustituir esta producción.

## Límite operativo

Vercel tiene conectado el repositorio y `main` es su rama de producción, con
creación de deployments habilitada (API consultada el 21 de octubre). Por tanto,
un merge puede disparar otro build. Antes del merge hay que probar el payload
integrado; después hay que comprobar el deployment y los alias. No se cambian
protecciones, permisos, facturación ni configuración de Vercel para este cierre.

Las pruebas locales y una revisión independiente son el criterio del owner; CI
de GitHub no es el gate de aceptación. Una revisión local no se presenta como
una aprobación formal de GitHub. La UAT humana pendiente sigue pendiente.

## Rollback del cierre, sólo por el owner

Si un build automático posterior al merge rompe el servicio, el objetivo de
recuperación es el deployment original de la tabla, que conserva las mejoras.
No se vuelve a desplegar el antiguo `main` ni se mueve el tag. Tras comprobar
que ese deployment sigue `Ready`, el owner puede restaurar ambos alias:

```bash
vercel alias set valio-demo-c54s2px1l-5513754018-9170s-projects.vercel.app valio-app.vercel.app --scope 5513754018-9170s-projects
vercel alias set valio-demo-c54s2px1l-5513754018-9170s-projects.vercel.app valio-demo.vercel.app --scope 5513754018-9170s-projects
```

Esperado: `vercel inspect` de cada dominio muestra el ID original y estado
`Ready`. Comprobar también carga, ficha y filtros en el navegador. Este guion
no ejecuta ni autoriza por sí mismo un rollback; registra la operación realizada.
